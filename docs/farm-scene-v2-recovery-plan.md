# 农场第二版纠偏与实施计划

日期：2026-09-28。状态：待实施。本次交付为计划，不表示下列视觉整改已经完成。

后续决定：用户已指定当前 scenic revision-2 为主场景，后续逻辑以该场景为基准。[主场景后续方案](scenic-main-scene-followup.md)优先于本文中“旧版仍默认”“重新确定整个场景”的历史约束。本文记录此前整改背景；尚未解决的问题不视为已完成。

本计划依据用户确认的方向制定：保留现有版本，将四边形场景空间区分为游戏地块与道路、河流等环境区域，继续使用 AI 生成游戏元素图片。目标是在真实游戏中呈现参考图的田园构图、空间关系和美术品质。

用户最新约束：不做无效测试和验收；视觉效果只在实施全部完成后由用户亲自查看。本计划不设置中途用户确认、不安排自动视觉评分或阶段效果验收。开发者只做必要的功能与资源检查，按参考完成实现，不替用户判定美术效果通过。

## 3. 逻辑世界与显示区域

### 3.1 不改变农业规则

保留所有已存在和后续探索产生的 `p{x}q{y}`、每单元 3×3、邻接、水源、行动报价、时间结算、计划及存档规则快照。不得删除田块、修改 ID 或以新开局代替兼容性验证。

新布局为每个游戏地块分配一个可追溯的显示区域，位置不写入游戏存档。道路、装饰河流和院落使用独立场景 ID，不把现有逻辑地块变成道路。改变显示间距不改变逻辑距离；布局尽量保持邻接关系在视觉上可理解。

区分真实水源地块与装饰河流。只有前者依照核心规则参与取水/灌溉；装饰河流不得通过文案、图标或行为暗示新增水源。已知真实水源应有可辨认的标识，相关条件面板继续说明实际来源。

### 3.2 区域类型与交互策略分离

| 区域类型 | 数据来源 | 点击语义 | 拖动 |
| --- | --- | --- | --- |
| 游戏地块 plot | 绑定 plotId，观察数据决定田、荒地、树林、水源或未知状态 | 可选择性和行动入口由现有规则决定 | 允许 |
| 道路 path | 显示布局 | 默认无游戏操作 | 允许 |
| 装饰河流 river | 显示布局 | 默认无游戏操作 | 允许 |
| 环境 environment | 显示布局：院落、花境等 | 默认无游戏操作 | 允许 |
| 桥 bridge | 连接道路并跨越指定河流区域 | 默认无游戏操作 | 允许 |

未知、树林和水源仍可属于游戏地块，不能以“不是农田”为由一律禁止选择。“不响应游戏点击”不等于屏蔽地图拖动。

拟定布局数据至少包含：`regionId`、区域类型、按一致绕序排列的边界点、可选 `plotId`、地面材质、连接边、绘制层次。交互能力由观察数据与区域职责派生；装饰节点另有落地点、锚点和遮挡范围。

## 4. 区域几何与空间分配

### 4.1 布局原则

四边形是主要构件，不要求所有构件同形同尺寸。田块使用经参考构图校准的四边形；道路和河流由具有真实宽度的区域组成；路口、河湾和边缘允许用额外多边形补齐。

逻辑单元映射为可重复扩展的显示单元。显示单元内部可留出道路、植被、河岸空间，单元边界声明连接位置。给院落等大型景观预留的空间必须在布局映射中处理，不能靠盖住地块实现。所有已有及将来的逻辑地块仍能获得有效位置。

相邻田块不再铺满全部平面：其间留出环境带，田埂属于明确的边界带，道路占有独立内部面积。禁止仅缩小贴图但保留铺满平面的命中框。

### 4.2 几何约束

- 游戏地块内部不得与道路或装饰河流内部相交。共享边允许，描边和植被的少量视觉溢出不改变区域归属。
- 桥是显式例外：桥跨越指定水域，桥头与道路连接，不能把普通道路与田地相交当作例外。
- 不允许两个游戏地块占有同一内部点。共享边上的选择规则必须确定，避免反复点击选择不同地块。
- 道路和水域连接使用共享的边界区间，校验宽度、两岸以及高低层关系；禁止只比较中心点或角点。
- 布局检查须覆盖初始院前、相邻区、负坐标与后续探索。合格初始地图不能掩盖扩展后的重叠。

### 4.3 绘制和命中

首轮通过参考图上的田块轮廓、主要路向和建筑落地点确定基准变换，不预先指定 2:1。用简单色块搭出可操作布局，确认映射和命中正常后记录新版布局规格，不设置阶段视觉验收。

田块图像、作物覆盖范围、选中描边、点击范围和小地图共用同一份几何。命中链为屏幕 → 镜头逆变换 → 世界坐标 → 区域候选 → 多边形判断。预留道路或不均匀间距后，不能继续只用旧投影的反函数推算唯一地块。

多边形用于定义区域和裁切，不意味着允许任意扭曲已有插画。正式图片按验证后的模板制作；运行时以统一尺度和锚点组合，必要裁切应在资产规格中明确。

### 4.4 未探索区域

所有未知地块保留逻辑身份。远处未知区域合并为连续雾层或统一未知地表，避免每格重复一张云雾图；可探索边界、被选中的未知地块和必要交互区域才显示明确轮廓。

合并视觉不合并规则，不展示未发现的地貌或资源。命中仍查询对应 plotId 和可达状态。区域合并与拆分不能改变探索结果，也不能消耗核心随机数。

## 5. 院前首屏设计

以 720×1280 为主构图基准，同时检查 390×844、430×932 和桌面竖屏画幅。屏幕边缘裁切是构图手段，但主要操作田应完整可见。

- 左上侧是房屋及院落，比例服从整体构图；可适当露出画外，不以房屋完整展示为优先目标。
- 中央及中下方突出可读的田块。院前田及其选择轮廓位于 HUD 排除后的地图可用区内。
- 河流、至少一个桥头或桥、道路和连续植被须在默认首屏参与构图，不能以“拖一屏能看到”通过。
- 树冠、花境、河岸形成前后层次；允许自然遮挡，但主要点击区域清晰，选中时可以降低遮挡或调整前景。
- 地图不是所有初始地块的总览。允许边缘田块露出一部分，避免用同屏中心点数量主导镜头。
- 参考图中的成熟麦田、幼苗和待办数不代表新局必有。必要状态检查使用独立会话，不向正式存档注入示例作物。

实施完成后提供可直接运行的新版入口，供用户查看真实首屏和田况。开发中可使用轮廓辅助图组织布局，不要求逐阶段截图、对比报告或视觉签字。

## 6. AI 美术制作流程

### 6.1 先定整体，再生成组件

制作一张与实际区域布局一致的院前场景标准图，确定田块形状、房屋比例、河流位置、植被层次、笔触、色彩和光照。标准图可以由 AI 辅助生成或编辑，但必须校准到已验证的布局。

标准图是风格和组合基准，不直接作为含固定作物及 UI 的游戏背景。整体图中的动态内容随后拆分制作。静态院落、河岸和花境可作为较大的环境块，土壤、作物、设施等动态部分保持独立。

禁止先批量生成全部零件，再以移动、翻转、拉伸拼出场景。首批只制作最小组合，接入游戏后修正轮廓套合、锚点或透明背景等实际问题，再扩充同规格元素；这是制作顺序，不是中途效果验收。

### 6.2 最小验证集与各类要求

| 类型 | 首批交付 | 内容边界 |
| --- | --- | --- |
| 地面 | 一块干土、同轮廓湿土、田埂 | 土壤不带作物和道路；湿土不默认画成积水水田 |
| 作物 | 小麦成长、成熟各一种 | 与土壤同模板；需要的行间和外部透明，不夹带第二层田框 |
| 道路 | 直段、路口及桥头过渡 | 有明确入口边和宽度，边缘能融入周围地表 |
| 河流 | 可拼接直段、转弯、两岸、桥 | 接口边水面和岸坡一致，流向可读 |
| 环境 | 房屋院落、一组树/灌木/花草 | 统一落地点与光向；避免把额外可耕田画死在院落里 |
| UI | 日期、资源、导航、选中标识 | 同一图形语言，真实尺寸下可辨认 |

先验证上述组合，再补充其他作物、土地用途、地貌、方向与区域变体。所有正式可用状态应有专用表现或明确且不误导的回退，不能让所有成熟作物永久显示成同一种叶菜。

### 6.3 每次生成的输入包

每个组件的输入必须包含：

1. 原始目标参考图和当前院前场景标准图。
2. 同批选定的相邻素材，用于统一笔触、颜色、光照和细节尺度。
3. 区域模板：轮廓、可绘制范围、裁切范围、连接边和锚点。
4. 实际显示尺寸、目标导出尺寸及放大倍率，禁止仅写“高清”。
5. 内容清单与排除项，例如土壤不含幼苗、图标不含文字、河段不自行新增桥。
6. 透明背景要求，以及必须保留的阴影、行间透明和边缘细节。

生成提示模板：

> 为田园游戏生成【素材类型与状态】。沿用附带场景标准图和选定素材的笔触、色彩、光照与物体比例。按几何模板的【轮廓、入口/出口边、锚点】构图，显示尺寸为【W×H】，输出尺寸为【导出尺寸】。必须包含【内容】，不得包含【排除项】。除【指定实体范围】外保持透明；保留【必要阴影/间隙】。不要自行更改视角、连接边位置、物体数量或添加 UI、文字、装饰边框。

工具支持时使用参考图编辑与局部重绘延续选定样式。每次只修正已指出的差距；若轮廓、比例或光向明显偏离模板，应重新生成该元素，不用非等比缩放补救。

### 6.4 朝向、透明与分辨率

- 河流、桥、建筑的不同朝向按需要分别制作；带明显光影的图片不能随意翻转。旋转或镜像复用只适用于经检查仍一致的无方向纹理。
- 不允许对正式插画使用非等比拉伸来凑轮廓。模板要求改变时，调整资产或重新生成。
- 实际检查 alpha 通道；棋盘背景画在图里不等于透明。纯色抠图仅用于可清晰分离的背景，必须复核半透明边缘、浅色花瓣和细叶，不能无条件阈值抠除。
- 生成尺寸可从实际显示尺寸的约 2 倍起步，最终倍率由游戏内清晰度和纹理预算确定；避免统一输出超大图后把细节全部缩没。
- 出图后保存原始文件、生成参数/提示词、所用参考、裁切与处理步骤。禁止覆盖唯一原稿。

### 6.5 组合制作与返修

每张素材须在统一背景下检查透明边缘，并在实际显示尺寸下与邻件组合检查。验证土壤/田埂/作物套合、河岸连接、道路过渡、光向、色彩、比例及重复感。

首批直接接入 Cocos 院前场景。格式检查和“生成成功”只证明产物存在，不证明效果达标。发现接缝、错位、黑白边或变形时定位到布局、模板或素材并修正；不额外制作评分工具、联系表验收流程或阶段效果报告。最终美术效果由用户统一查看。

## 7. 渲染、HUD 与模块调整

在现有 `view/world/scenic/` 下分步引入区域能力，避免重新搭建无关框架：

| 文件或模块 | 整改职责 |
| --- | --- |
| `ScenicRegionLayout.ts`（新增） | 区域类型、边界、逻辑地块映射、连接边、装饰锚点 |
| `ScenicLayoutValidation.ts`（新增） | 区域重叠、裂缝、连接宽度与映射完整性检查 |
| `ScenicProjection.ts` | 按新模板提供变换，移除作为唯一地图结构的固定菱形假设 |
| `ScenicHitTest.ts` | 根据区域多边形命中，统一点击、描边和选择行为 |
| `ScenicWorldView.ts` | 消费区域布局，分层绘制，去掉穿田道路与满屏雾瓦片 |
| `ScenicChunkStore.ts` | 围绕可见区域缓存，纳入跨块物体包围盒，避免边缘提前卸载 |
| `ScenicMinimap.ts` | 使用同一布局映射和真实观察；裁切视窗框，明确家与所选田 |
| `FarmViewModel.ts` | 提供 scenic 专用短田况、水分和选中田待办；避免旧版多行文案混用 |
| `ScenicHud.ts` / `DistrictNavigator.ts` | 紧凑导航、正确文本高度、对比度、安全区及触摸范围 |

地面、道路/河流、田况/作物、建筑/前景、选中提示各有职责。通过区域布局消除地面占用冲突；仅调整层级不能修复道路穿田。直立物的深度顺序应跨块一致，不能只在各个 chunk 内排序。

HUD 使用 scenic 一致的主题数据，避免新地图颜色来自新素材包、卡片颜色却仍由旧风格决定。田况文字长度与布局一起设计；动态文字不能依靠 CLAMP 悄悄截断。待办徽标说明是选中田待办还是全局待办，不能把全局数量当成当前田况。

小地图和分区标签遵循参考的紧凑布局；展开后为主要田块保留操作空间。日期/资源在窄屏不越界；导航选中状态可辨认。

## 10. 必要检查与最终效果查看

### 10.1 仅保留会影响正确性的检查

- 新区域映射能命中正确 plotId，田块内部不与普通道路/河流重叠；检查代表性的边界、负坐标及扩展情形即可。
- 选田、拖动、缩放和区域定位可用；两版切换不改变游戏存档或 revision，旧版仍能正常启动和操作。
- 田况、作物与水源表现来自真实观察，新增图片能加载，实际产物包含本次修改。
- 复用有价值的现有检查。固定旧菱形参数、只数中心点、用矩形范围推导“美术通过”等断言应删改；只针对真实风险补充检查，不另建通用验收框架。
- 本轮实现完成时运行必要的回归与构建。通过后不重复运行；只有新改动、失败或明确问题才追加相关检查。

### 10.2 不安排的工作

- 不做自动视觉相似度评分、逐阶段美术评级、提交数量统计或大批截图验收。
- 不为了满足任意次数而固定执行 20 次切换，不进行与本轮改动无关的压力测试或全量测试扩张。
- 不提前开展真机矩阵、强制 fps 门槛或完整性能基准项目。出现卡顿、泄漏或用户明确提出性能要求时，再针对问题测量。
- 不要求用户中途看灰盒、选素材或验收单个阶段。

### 10.3 实施完成后由用户看效果

交付时提供实际可运行的版本、明确入口和必要说明，保留旧版切换。用户亲自判断构图、素材融合、整体观感和与参考的距离；开发者不以测试通过代替这一判断。

默认展示真实游戏状态，用户需要看成长/成熟等状态时提供独立演示会话，避免修改其原存档。最终截图按需要提供，不作为运行版本的替代品。

将“实现与必要检查完成”和“用户认可效果”分别表述；未得到用户评价前，不宣称视觉已验收通过。

## 11. 风险与处理

| 风险 | 处理 |
| --- | --- |
| AI 单图好看但视角/比例不一致 | 使用标准图和几何模板，首批直接组合进游戏再扩充 |
| 不规则布局使后续地块没有位置 | 确定可扩展单元映射及边界连接，测试正负坐标与实际探索 |
| 显示河流被误认为新增水源 | 区分真实水源标识与装饰水域，规则条件保持原定义 |
| 植被层次与交互相冲突 | 用遮挡范围、选择提示与透明处理解决，不机械清空所有植被 |
| 旧存档缺少布局字段 | 布局独立派生，不向存档增加强制字段，不迁移规则快照 |
| 资源批量制作后才发现构图错误 | 先完成区域布局，再制作最小组合，避免先大量出图 |
| 大图和细节提高资源成本 | 按实际显示尺寸导出，基于测量决定合图与缓存 |
